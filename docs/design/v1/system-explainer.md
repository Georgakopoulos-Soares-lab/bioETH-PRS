# bioETH PRS — System Explainer

> A bottom-up explanation of what is implemented, how it works, and what the
> benchmark findings mean.  Written to be readable without prior FHE knowledge.

---

## The problem being solved

A Polygenic Risk Score (PRS) is a prediction of genetic disease risk: take a
person's DNA (represented as thousands of SNPs — single nucleotide polymorphisms,
basically genetic variant counts of 0, 1, or 2), multiply each one by a
research-derived weight (beta from a GWAS study), and sum the products.  That is a
dot product.

The problem: doing this privately.  The patient does not want their DNA visible to
the model owner.  The model owner may not want their weights visible to the patient.
And you want the computation to be trustless — no server can cheat.

This project's answer: run the entire dot product **inside Fully Homomorphic
Encryption on the blockchain**.  The EVM never sees raw DNA or raw weights.  It
only touches ciphertexts.

---

## The four contracts and what they each do

### 1. `GenomicRegistry` — the identity / access layer

The simplest contract.  It is a URI registry: each patient registers their sample
(a pointer to their encrypted genomic data on IPFS/Arweave) and gets a `sampleId`.
The registry maintains an ACL mapping — who is allowed to request a PRS computation
using which sample.

```solidity
registerSample(uri)               // stores URI + owner, returns sampleId
grantAccess(sampleId, grantee)    // allows another address to use your sample
hasAccess(sampleId, caller)       // used by the compute engine as a gate
```

The key point: **the sample data itself never enters the chain**.  The URI is just a
pointer.  The registry is purely for access control — preventing someone from running
a PRS job with your DNA without your permission.

---

### 2. `ModelMarketplace` — the GWAS model storage layer

A researcher who has a GWAS model (e.g. 100 SNP weights from a published study)
publishes it here.  The model goes through a **chunked lifecycle** rather than
uploading all at once, because a 5000-weight array will not fit in a single
transaction:

```text
createModelShell(...)  →  appendPublicModelChunk() × N  →  finalizeModel()
```

`createModelShell` declares the metadata: how many weights, what chunk size, and
crucially — `weightZeroPoint` and `scoreOffset` (explained in the quantization
section below).  The shell is a header with no data yet.

Then the researcher appends weight chunks one transaction at a time.  Each chunk is
validated to be the exact expected size and index — no gaps, no out-of-order uploads.

`finalizeModel` locks the model.  It cannot be changed after this point.

**Two modes:**

| Mode | Storage type | Who can read weights | Gas cost |
| --- | --- | --- | --- |
| Public | `uint64[]` | Anyone | Lower |
| Private | `euint64[]` (encrypted) | Authorized readers only | Higher |

The marketplace stores `weightZeroPoint` and `scoreOffset` on every model header.
These are the two correction constants that make V1 quantization work correctly
(see below).

---

### 3. `PRSComputeEngine` — the computation layer

This is the core contract.  It runs an encrypted dot product across multiple
transactions using a state machine.  Each job goes through five phases:

```text
createPRSJob(modelId, sampleId)
        ↓
appendSnpChunk(jobId, encryptedSnps, inputProof)  × N
        ↓
finalizeSnpUpload(jobId)
        ↓
computeChunk(jobId)  × N
        ↓
finalize(jobId)  →  emits JobFinalized(encodedScore)
```

**`createPRSJob`** — gates on registry ACL (`hasAccess`), reads model config from
marketplace, initializes a `Job` struct with an encrypted zero (`FHE.asEuint64(0)`)
for both `partialSum` and `genoSum`.

**`appendSnpChunk`** — the patient submits their SNP values encrypted.  The type is
`externalEuint64[]` + `bytes inputProof`.  The proof is a cryptographic bundle
generated by `fhevmjs` that the on-chain `InputVerifier` validates.  Each SNP goes
through `FHE.fromExternal(encryptedSnps[i], inputProof)` to convert from user-submitted
external handle to a contract-owned ciphertext, then `FHE.allowThis(snp)` grants the
contract FHE permission on it.

**`finalizeSnpUpload`** — locks the SNP payload.  Nothing can be changed after this.
Compute can only begin once this call succeeds.

**`computeChunk`** — for each chunk, loads the model weights and matching SNP chunk,
then runs the inner FHE loop:

```solidity
// Public model path:
for (uint256 i = 0; i < publicWeights.length; i++) {
    acc = FHE.add(acc, FHE.mul(snps[i], FHE.asEuint64(publicWeights[i])));
    genoAcc = FHE.add(genoAcc, snps[i]);
}
```

`FHE.mul` and `FHE.add` operate on ciphertexts.  The EVM calls FHE precompiles — on
the mock this is plaintext arithmetic behind the scenes; on Sepolia this is real TFHE.
`genoSum` tracks the sum of all SNP dosages in parallel — it is needed for the
quantization correction at the end.

**`finalize`** — applies the V1 correction and emits the result:

```solidity
euint64 withOffset  = FHE.add(job.partialSum, FHE.asEuint64(job.scoreOffset));
euint64 correction  = FHE.mul(job.genoSum,    FHE.asEuint64(job.weightZeroPoint));
euint64 encodedScore = FHE.sub(withOffset, correction);
FHE.allow(encodedScore, msg.sender);
emit JobFinalized(jobId, msg.sender, encodedScore);
```

`encodedScore` is an encrypted handle.  Only `msg.sender` has the FHE ACL permission
to decrypt it.

### 4. `ResultOracle` — DP noise + classification

Sits on top of the engine.  Takes an encrypted score, adds differential privacy
noise, and maps it to a risk category (`euint8` — low / medium / high).  This is the
only place a value becomes "publicly decryptable" — and only the category, never the
raw score.

**Noise is generated entirely on-chain.**  The constructor takes a `uint64 noiseUpperBound`
(immutable; must be a positive power of two — required by the fhEVM coprocessor).  Every
`classify()` call draws `noise = FHE.randEuint64(noiseUpperBound)`, which is uniform over
`[0, noiseUpperBound)` and unknowable to the caller before the transaction is mined.

```solidity
euint64 noise = FHE.randEuint64(noiseUpperBound);
FHE.allowThis(noise);
euint64 noisy = FHE.add(score, noise);
```

The caller provides the encrypted score and thresholds but has zero influence over the
noise value.  This closes the previous loophole where passing `encrypt(0)` as noise
would silently defeat DP.

**Why uniform noise, not Laplacian:** Formal DP requires Laplacian-calibrated noise.
Generating it inside FHE requires an inverse-CDF approximation circuit — significant
gate/HCU cost.  Uniform noise via `FHE.randEuint64` is a single precompile call,
prevents the trivially-zero probe attack, and is honest about its weaker guarantee.
Laplacian calibration is deferred to the research phase.

## The fhEVM plumbing

**`ZamaEthereumConfig`** — all three FHE contracts inherit this base contract.  It
auto-detects the chain ID at runtime and wires the correct Zama coprocessor, KMS
gateway, and input verifier addresses.  On chainId 11155111 (Sepolia) it uses the
real Zama infrastructure; on 31337 (Hardhat) it uses the in-process mock.  Same
bytecode, different runtime behaviour — no contract changes are needed to switch
networks.

**`FHE.allowThis(handle)`** — every time the contract creates or receives an
encrypted value it wants to keep, it must call this.  It writes an ACL entry that
tells the coprocessor "this contract is allowed to use this ciphertext handle."
Without it, any subsequent transaction that tries to use the handle will be rejected.

**`FHE.allow(handle, userAddress)`** — grants FHE permission to an external address.
`finalize` calls this before returning the score handle.  Without it, the user cannot
decrypt.

**Decryption — two paths:**

| Environment | Call | What happens |
| --- | --- | --- |
| Local Hardhat (mock) | `fhevm.debugger.decryptEuint(type, handle)` | Reads plaintext directly from mock coprocessor state.  Instant. |
| Sepolia (real FHE) | `fhevm.userDecryptEuint(type, handle, contract, signer)` | User EIP-712 signs a re-encryption request → Zama relayer → KMS decrypts under user's key → returns plaintext. |

The validation script uses `fhevm.isMock` to choose the correct path automatically.

## The quantization math — why it works

GWAS betas are signed floats like `-0.31`, `+0.08`.  The FHE type `euint64` is an
unsigned 64-bit integer.  You cannot store `-0.31` there directly.  V1 solves this
in three steps.

### Step 1 — scale to integers

Pick a scale (e.g. 3,000,000).  Multiply each float:

```text
-0.31 → round(-0.31 × 3,000,000) = -930,000
+0.08 → round(+0.08 × 3,000,000) = +240,000
```

Now you have signed integers `q_i`.

### Step 2 — shift to unsigned (remove negative weights)

Find the most negative weight and use it as the zero-point:

```text
weightZeroPoint = -min(q_i)
u_i = q_i + weightZeroPoint          (all u_i are now ≥ 0)
```

These unsigned values are what get stored in the contract.

The dot product `Σ(g_i × u_i)` now includes a spurious extra term:
`weightZeroPoint × Σ(g_i)`.  To remove it you need `genoSum = Σ(g_i)`, which the
engine accumulates in parallel during `computeChunk`.

### Step 3 — shift the final score to unsigned

The corrected score `raw_score_q = partialSum − weightZeroPoint × genoSum` can still
be negative for a low-risk patient.  Compute the worst-case score:

```text
raw_min = Σ(2 × min(q_i, 0))         (all dosages = 2, all weights negative)
scoreOffset = −raw_min
encodedScore = raw_score_q + scoreOffset    (always ≥ 0)
```

The contract computes this in one rearranged expression to avoid any intermediate
unsigned underflow:

```solidity
encodedScore = (partialSum + scoreOffset) − (weightZeroPoint × genoSum)
```

### Worked example

| Step | Values |
| --- | --- |
| Float weights | `[-0.30, 0.10, 0.25]` |
| Scale = 100 → signed ints | `[-30, 10, 25]` |
| weightZeroPoint = 30, shift | `[0, 40, 55]` |
| Genotypes | `[0, 2, 1]` |
| Dot product with shifted weights | `0×0 + 2×40 + 1×55 = 135` |
| genoSum | `0 + 2 + 1 = 3` |
| Correction | `135 − 30×3 = 45` ← matches `0×(−30) + 2×10 + 1×25 = 45` |
| raw_min = −60 → scoreOffset = 60 | `encodedScore = 45 + 60 = 105` |
| Decode off-chain | `(105 − 60) / 100 = 0.45` |

To decode off-chain: `raw_score_q = encodedScore − scoreOffset`, then
`prs = raw_score_q / scale`.

## What the benchmark findings mean

### The 100-SNP mock run (`npm run validate:mock`)

Total gas: **18.6M**.  Score: 758,685 — matches expected plaintext dot product.
All protocol checks pass: ACL gate, `JobFinalized` event, encrypted handle, decryption.

| Phase | Gas | % | What is happening |
| --- | ---: | ---: | --- |
| Upload SNPs | 10,005,065 | 54% | 11 chunks × `appendSnpChunk`. Each call writes 10 encrypted handles to storage — cold `SSTORE` is expensive. |
| Compute | 6,458,236 | 35% | 11 chunks × ~622K. Each call does 10× `FHE.mul` + `FHE.add` pairs plus genoAcc accumulation. |
| Publish model | 1,675,915 | 9% | One-time cost. Paid once by the researcher, amortized across all users of this model. |
| Finalize | 154,791 | <1% | Fixed cost regardless of SNP count. |
| Create job | 291,152 | 2% | Fixed cost. |

**The gas pattern confirms the architecture is correct.**  Upload dominates because
you are storing 101 ciphertext handles in contract storage — that is inherently
expensive.  Compute is cheaper per-SNP because FHE multiply does not write new
storage; it operates on existing handles.

The first compute chunk costs 654K (cold `partialSum` slot initialization).  All
subsequent full chunks cost 622K (warm storage).  The final partial chunk (1 SNP,
not 10) costs only 198K — exactly what you expect from linear scaling.

### The HCU ceiling probe (`npm run probe:hcu:mock`)

The probe tested five candidate chunk sizes systematically and found:

| chunkSize | FHE ops (3 per SNP) | Result |
| ---: | ---: | --- |
| 10 | 30 | PASS |
| 15 | 45 | PASS |
| 20 | 60 | PASS |
| 25 | 75 | FAIL — `HCUTransactionLimitExceeded` |
| 32 | 96 | FAIL — `HCUTransactionLimitExceeded` |

**The mock HCU budget is ~60-74 ops/tx — not ~30 as previously documented.**  The
prior claim was inferred by testing only chunkSize=32 (fail at 96 ops) against an
assumed 30-op budget.  Nobody had tested the intermediate sizes.

**What a larger chunk size buys you:**

| | chunkSize = 10 | chunkSize = 20 |
| --- | ---: | ---: |
| 100-SNP transaction count | 25 tx | 13 tx |
| 5000-SNP transaction count | 1005 tx | 503 tx |
| Gas per SNP (compute phase) | 62,275 | 55,109 |

Doubling the chunk size halves transaction count and saves ~11% gas per SNP because
the fixed per-chunk overhead (state machine bookkeeping, `partialSum` read/write) is
amortized over more SNPs.

### What mock cannot tell us

The mock coprocessor performs **plaintext arithmetic** behind the scenes.  It
validates the full fhEVM protocol — handles, ACL, input proofs, event emission — but
the numbers used in gas and timing measurements are not those of real TFHE:

- **Real ciphertext latency**: TFHE bootstrapping adds seconds per operation.  The
  mock's 6 ms per chunk will become minutes on Sepolia.
- **Real precompile gas costs**: Zama's fhEVM precompiles have a different gas
  schedule than the mock.  Compute gas in particular will change significantly.
- **Sepolia HCU ceiling**: the mock's ~60-74 ops/tx is a local development constant.
  The real Sepolia coprocessor may allow 300 or 1000 ops/tx.  At 300 ops, chunkSize
  could reach 100, dropping a 5000-SNP job from ~1000 transactions to ~100.  This is
  measured by `npm run probe:hcu` on Sepolia.
- **KMS re-encryption round-trip**: the `userDecryptEuint` path (EIP-712 signing →
  Zama relayer → KMS → plaintext) has not been tested yet.  It only runs on Sepolia.

## One-sentence summary

> We took the PRS dot product formula from a 2025 genomics paper, replaced the
> floating-point weights with quantized unsigned integers, and implemented the entire
> computation as an FHE state machine across multiple Ethereum transactions — so a
> smart contract computes a patient's genetic risk score without ever seeing their DNA
> in plaintext.
